# Environment setup

## Prerequisites

* Docker Desktop (Windows/macOS) or Docker Engine + Compose v2 (Linux). This is the only hard requirement.
* Python 3.11+, only to run the test suite and tooling locally (`scripts/verify`).

## First run

```powershell
# Windows
.\scripts\setup.ps1      # creates .env (generated JWT secret + demo password), starts PostgreSQL,
                         # builds the API image, validates config, migrates, seeds demo data, creates .venv
.\scripts\start.ps1      # starts db + api, waits for /ready
```
```bash
# Linux / macOS
./scripts/setup.sh && ./scripts/start.sh
```

Then open `http://127.0.0.1:8000/docs`. Demo login: `DEMO_OWNER_EMAIL` / `DEMO_OWNER_PASSWORD` from `.env`.

| Script | Does |
|---|---|
| `setup` | prerequisites, `.env`, PostgreSQL health, image build, config check, migrations, seed, venv |
| `start` | `docker compose up -d --build`, waits for `/ready` |
| `stop` | stops containers; the database volume is preserved |
| `verify` | ruff, format, migrations + `alembic check`, OpenAPI drift, pytest, live `/ready` |
| `backup` | `pg_dump -Fc` into `backups/`, verified with `pg_restore --list` |
| `restore` | restores a dump (requires `-Confirm` / `--confirm`) |

Every script checks exit codes and stops with `FAILED …` and a non-zero exit code on any failure.

## Demo data

`python -m app.cli seed` is idempotent. Re-running it never duplicates customers, invoices, payments or bills, and
existing records are left alone. Scenario dates (Ramesh's invoice due in 10 days, his commitment in 5, the overdue
invoice, the upcoming bills) are relative to the day the demo business was **first** seeded, so they drift as days
pass.

To start the scenarios from today again, in **development or test only**:

```bash
python -m app.cli seed --reset      # or: docker compose run --rm --no-deps --entrypoint python api -m app.cli seed --reset
```

The reset only touches the business that has **both** the demo owner's email (`DEMO_OWNER_EMAIL`) and the name
"KAIRA Demo Traders". It deletes that business's rows and then seeds again. It refuses in staging and production, and
`--force` cannot override it there. It refuses an account that does not belong to the demo business. No other
business is touched.
